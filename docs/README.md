# HackAgent Documentation

The Docusaurus site served at https://docs.hackagent.dev.

## Requirements

- [uv](https://docs.astral.sh/uv/) for the Python side (API reference generation)
- Node.js 20+ and npm

## Quick start

```bash
# From the repository root: generate the campaign-file pages, the command
# list and the attack partials
uv run python docs/scripts/generate_reference.py
# ...and the SDK module reference from docstrings
uv run python docs/scripts/generate_docs.py

# From docs/
npm ci
npm start           # dev server with live reload
npm run build       # production build into build/
npm run serve       # serve the production build
npm run typecheck   # tsc over the site config
```

`npm run generate-docs` runs the SDK generator from `docs/`.

## Information architecture

The site has four navbar tabs. Each has one job; put a page in the tab whose
reader it serves.

| Tab | Reader | What goes there | Folder |
|---|---|---|---|
| **Guides** | Anyone learning HackAgent | Introduction, Getting Started, Concepts, **Attacks** (one page per attack, grouped by type), AI Risks, Security & Ethics. Explanations, tutorials, how to choose | `docs/` (root pages), `docs/attacks/` |
| **SDK** | Python users | Overview, **Guides** (tasks done from Python), **Reference** (every public module, generated) | `docs/sdk/`, `docs/hackagent/` |
| **CLI** | Command-line users | Overview, configuration, **Campaign files** (every field of the format, generated), **Commands** (every command and option, generated) | `docs/cli/` |
| **API** | People calling the HTTP API directly | The REST API and the LLM gateway | `docs/api/` |

How the sidebars are built (`sidebars.ts`):

- **Autogenerated from the folder**: `docs/attacks/` (the Attacks category in
  Guides), `docs/sdk/guides/` (SDK > Guides), `docs/cli/` (the whole CLI tab)
  and each package under `docs/hackagent/` (SDK > Reference). Add a page to
  one of these folders and it appears; order it with `sidebar_position` in
  its front matter, and name a subfolder with a `_category_.json`. Leave gaps
  between positions so a page can go in between.
- **Listed by hand**: the rest of Guides (Getting Started, Concepts, AI Risks,
  Security & Ethics) and the API tab. A new page there must be added to
  `sidebars.ts`.

## Layout

| Path | What it is |
|---|---|
| `docs/` | Hand-written pages (`.md` is CommonMark, `.mdx` is MDX) |
| `docs/attacks/<type>/<name>.mdx` | Hand-written attack pages, one per attack in the registry, in a folder per type: `static`, `adaptive`, `multi-turn`, `indirect` |
| `docs/attacks/**/_*.generated.mdx` | **Generated** partials the attack pages import: `_<name>.generated.mdx` (helper models, parameters, campaign snippet), `_list.generated.mdx` per type, `_catalog.generated.mdx` for the overview |
| `docs/cli/campaign-files/`, `docs/cli/commands.md`, `static/schema/campaign.schema.json` | **Generated** from the campaign spec, the attack registry and the Click tree by `scripts/generate_reference.py`. Edit the code, not these files; CI fails when they drift |
| `docs/hackagent/` | **Generated** SDK module reference. Do not edit by hand; CI regenerates it on every build, so the committed copy may lag |
| `docs/risks/vulnerabilities/` | **Generated** from `hackagent/catalog/risks` by `scripts/risk_pages.py`. Edit the catalog, not these pages |
| `sidebars.ts` | The four navbar sidebars (Guides, SDK, CLI, API) |
| `docusaurus.config.ts` | Site config and navbar |
| `scripts/generate_docs.py` | The SDK reference generator |
| `scripts/generate_reference.py` | The campaign-file, command and attack-partial generator |
| `static/` | Images and other files served as-is |

The build fails on broken links, broken anchors, and unresolved `.md`/`.mdx`
links. When you move or rename a page, update every link to it; the old URL
simply goes away.

## Page components

These are available in every `.mdx` page without an import (`src/theme/MDXComponents.tsx`). A `.md` page is plain CommonMark and cannot use them; rename it to `.mdx` first.

| Component | Use it for |
|---|---|
| `<Tabs>` / `<TabItem>` | Alternatives the reader picks between: SDK / CLI / TUI, pip / uv, one goal source or another. Give related tab sets the same `groupId` so a choice carries across the page |
| `<Term id="judge">judges</Term>` | An inline concept that opens its definition in a modal |
| `<ConceptGrid ids={['target', 'attack']} />` | Cards for several concepts, each opening its definition |
| `<Modal trigger="…" title="…">` | Detail that would interrupt the page: advanced flags, a full config, background. Add `wide` for media |
| `<Screenshot src="…" alt="…" title="…">` | A thumbnail that opens the full-size image in a modal; wrap several in `<ScreenshotGrid>` |

Concept definitions live in one place, `src/components/Glossary/terms.tsx`, so a concept reads the same on every page. Add a term there before using it.

In `<Modal>` and `<TabItem>`, leave a blank line after the opening tag so the content is parsed as Markdown. Modal content renders only when opened, so the build cannot check the links inside it; `scripts/check_modal_links.py` does, after `npm run build`, and CI runs it.

## What the generator does

`scripts/generate_docs.py`:

1. Installs the `docs` dependency group (`uv sync --group docs`).
2. Discovers every module under `hackagent/`, skipping private modules and
   the runnable scripts in `hackagent.examples`.
3. Runs pydoc-markdown with a patched escaper (see the comments in the
   script for the pydoc-markdown 4.8.2 bugs it works around).
4. Writes `docs/hackagent/`, makes the output safe
   for MDX, and renames the web interface pages so the docs plugin
   publishes them. It deletes the `sidebar.json` pydoc-markdown writes,
   since `sidebars.ts` builds the SDK sidebar from the pages themselves.
5. Runs `scripts/risk_pages.py`, which writes one page per risk from the
   catalog's vulnerability classes, sub-type enums and threat profiles.

## CI

`.github/workflows/docs.yml` runs on pushes and pull requests that touch
`docs/` or `hackagent/`: it checks that the generated reference matches the
code, typechecks the site, regenerates the SDK reference, builds, and checks
the links inside modals. It does not deploy.

## Style guide

### Voice

Write the way `docs/concepts/attacks-and-roles.md` reads:

- **Plain and short.** One idea per sentence. Prefer common words: "use",
  not "leverage"; "about", not "approximately".
- **Second person, present tense.** "You run a campaign", "the attack sends".
  Not "we", not "the user", not "will".
- **Concrete.** Name the field, the command, the number. "PAIR sends up to 25
  prompts per goal" beats "PAIR can be expensive".
- **Say what to do and why.** Lead with the action or the conclusion, then the
  reason. Cut throat-clearing ("It is worth noting that…").
- **No marketing.** No "powerful", "seamless", "cutting-edge". No emoji.
- **Headings are sentence case** and say what the section answers.

### Generated from code vs hand-written

Facts that live in the code are generated; explanations are written by hand.

- **Generated**: every field of the campaign format, every attack's helper
  models and parameters with their defaults, the minimal campaign snippet,
  the attack lists, every CLI command and option, the SDK module reference.
  Change the code (a `Field(description=...)`, a docstring, a Click help
  string) and regenerate; never edit a generated file.
- **Hand-written**: what an attack does and why it works, when to use it,
  what it costs, how to read its results, tutorials and concepts.
- **Do not restate generated tables in prose.** Render the partial or link to
  the generated page instead. A hand-written sentence may name a parameter
  to explain a decision ("raise `streams` when…"), but must not copy its
  default or its description, which would drift.

### The attack page template

Every attack has one page, `docs/attacks/<type>/<name>.mdx`, where `<type>`
comes from the attack's module in `hackagent/attacks/techniques/`
(`multi_turn` becomes `multi-turn`). Its front matter has `title` (the
attack's display name), `description` (one line) and `sidebar_position`. It
imports its partial at the top:

```mdx
import Generated from './_<name>.generated.mdx';
```

and has exactly these sections, in this order (`tests/unit/docs/test_attack_pages.py`
checks the `##` headings, the import and the render):

| Section | What it must contain |
|---|---|
| Intro (no heading) | One or two short paragraphs: what the attack does to the target, and the one idea that makes it work |
| `## At a glance` | A one-row table: Type \| Helper models \| Turns \| Calls per goal \| Good for |
| `## Research` | The paper or reference implementation (authors, year, link), what it showed, and where HackAgent's version differs |
| `## How it works` | Numbered steps from goal to verdict, then a `mermaid` diagram of the same flow |
| `## When to use it` | The targets and situations it suits, and when another attack is the better choice (link it) |
| `## Cost` | Target, helper-model and judge calls per goal with the defaults, and which parameters raise or lower that |
| `## Configuration` | `<Generated />` first (its `###` sections are Helper models, Parameters, In a campaign file), then one or two hand-written example campaigns, each with a one-line caption saying when to use it |
| `## Reading the results` | What success, failure and error look like in the results and the dashboard, and what to check first |
| `## Limitations` | What it cannot find, how it can mislead, gaps compared with the paper |
| `## Related` | Links to related attacks, concept pages and risks |

Use `###` inside a section if you need sub-headings. The type pages
(`docs/attacks/<type>/index.mdx`) have an intro, `## What they have in
common`, `## The attacks` (renders `_list.generated.mdx`) and `## Choosing
between them`. The overview (`docs/attacks/index.mdx`) renders
`_catalog.generated.mdx` under `## All attacks`.

Comments in `.mdx` are `{/* ... */}`; MDX has no HTML comments. A `.md` page
is CommonMark and cannot import partials or use components.

### Verifying locally

Run these from the repository root before you push; CI runs the same:

```bash
uv run python docs/scripts/generate_reference.py --check
uv run pytest tests/unit/docs -q
uv run ruff check . && uv run ruff format --check .
(cd docs && npm run typecheck && npm run build)
python docs/scripts/check_modal_links.py docs
```

`npm run build` fails on any broken link or anchor. If a command regenerates
the SDK reference under `docs/hackagent/`, do not commit those pages
(`git checkout -- docs/docs/hackagent`).
